# Spinel v1 技術方針

- Status: v1 Final
- 確定日: 2026-07-27
- 対象バージョン: Spinel v1

## 1. 文書の目的

この文書は、[Spinel v1 プロダクト要件](product-requirements.md)を実現するための採用技術、アーキテクチャ上の制約、セキュリティ境界、運用・品質方針を確定する。

本書は実装詳細設計ではない。内部API、テーブル、モデル、クラス、ディレクトリ構成、具体的なジョブ実装など、今回決定していない事項は「詳細設計で決定」とする。

v1確定後に意味的な変更を加える場合は、既存の決定を無断で上書きせず、対象バージョンと改訂履歴を更新する。

## 2. 技術選定

### 決定事項

| 領域 | 採用方針 |
| --- | --- |
| 言語 | Python |
| Webフレームワーク | FastAPI |
| HTML生成 | サーバーサイドテンプレート |
| 画面更新 | HTMX |
| ブラウザスクリプト | 必要最小限の素のJavaScript |
| スタイル | 素のCSSとCSSカスタムプロパティ |
| データベース | SQLite |
| DBアクセス | SQLAlchemy 2 |
| スキーマ変更 | Alembic |
| Python管理 | `uv` と `pyproject.toml` |
| 実行・配布 | Docker |
| CI | GitHub Actions |

### 理由

- 単一ユーザー向けアプリケーションに適した小さな構成を維持する。
- サーバー側を状態と画面の正とし、SPA固有の複雑さを導入しない。
- HTMXだけで不自然になるフォーカス復帰や画面更新は、小さなJavaScriptで補助する。
- CSSやフロントエンドのための独立したビルド基盤を必須にしない。
- SQLiteでも継続的な更新を安全に行えるよう、明示的なマイグレーションを最初から持つ。

### 対象外

- React、Vue等によるSPA
- PostgreSQL等の外部DBを必須とする構成
- 複数Webワーカーによる水平分散
- フロントエンド専用の大規模なビルドパイプライン

## 3. アーキテクチャ上の制約

- **TP-ARCH-001:** v1は単一ユーザー、単一アプリケーションインスタンス、単一Webワーカーで動作させる。対応要件: `PR-CTX-001`
- **TP-ARCH-002:** Web処理、定期収集、保持期限処理は同じアプリケーションプロセスで実行できる構成とする。
- **TP-ARCH-003:** 同一日界のデッキ生成は、複数タブや再試行があっても1つだけ確定するよう冪等性を保証する。対応要件: `PR-DECK-001`, `PR-DECK-004`, `PR-DECK-006`
- **TP-ARCH-004:** デッキ生成中にプロセスが停止した場合、再起動後に安全に再試行または再開できる設計とする。
- **TP-ARCH-005:** 生成済みデッキは、その後の収集、設定変更、購読解除によって書き換えない。対応要件: `PR-DECK-006`, `PR-DECK-010`, `PR-SUB-004`
- **TP-ARCH-006:** UIはサーバー生成HTMLを基本とし、HTMXによる部分更新を使用する。公開JSON APIの提供はv1の目的としない。

### 理由

SQLiteとアプリ内定期処理を安全かつ単純に運用するため、複数ワーカーをサポートしない。将来複数ユーザー化や水平分散を行う場合は、DB、ジョブ実行、排他制御を含めて別バージョンの設計判断とする。

## 4. 収集・生成・保持

- **TP-FETCH-001:** 登録されたフィードを6時間ごとに定期取得する。対応要件: `PR-SUB-001`, `PR-SUB-005`
- **TP-FETCH-002:** 日界後のデッキ生成前にも全購読元を取得し、取得処理の完了後に選抜する。対応要件: `PR-DECK-004`, `PR-DECK-005`
- **TP-FETCH-003:** フィード取得ではETagとLast-Modifiedを利用できる場合に条件付きリクエストを行い、配信元と通信量への負荷を抑える。
- **TP-FETCH-004:** 同一記事を繰り返し取得しても重複登録しない一意性を保証する。記事識別子の具体的な生成規則は詳細設計で決定する。
- **TP-FETCH-005:** 取得失敗は他の購読元の収集やデッキ生成を妨げない。成功済みの候補だけでデッキを生成する。対応要件: `PR-SUB-005`, `PR-SUB-006`
- **TP-FETCH-006:** 公開日時が欠落または不正な記事は初回取得日時を保持し、候補期間の判定に使用できるようにする。対応要件: `PR-DECK-007`
- **TP-RET-001:** 記事と関連する処理履歴を初回取得から7日後に自動削除する。対応要件: `PR-SRCH-006`
- **TP-RET-002:** 削除処理は生成中または有効な当日デッキの参照整合性を壊さない。

取得の並行数、タイムアウト、再試行回数、応答サイズ上限、スケジューラの具体的なライブラリは詳細設計で決定する。

## 5. 永続化

- **TP-DATA-001:** SQLiteファイルはDockerの永続ボリュームに保存する。
- **TP-DATA-002:** SQLiteの外部キー制約を有効にする。
- **TP-DATA-003:** 並行するWeb操作と収集処理を想定し、WALモードと短いトランザクションを使用する。
- **TP-DATA-004:** スキーマ変更はAlembicのバージョン付きマイグレーションとして管理する。
- **TP-DATA-005:** デッキ生成、カード操作、取り消しは、途中状態が外部から観測されない単位でトランザクション化する。

テーブル名、列、リレーション、列挙値、インデックスは詳細設計で決定する。プロダクト要件で定めた状態遷移と保持期間を変更してはならない。

## 6. セキュリティ境界

### 認証と通信

- **TP-SEC-001:** Spinel本体にはユーザー登録やアプリ内認証を実装しない。対応要件: `PR-CTX-001`
- **TP-SEC-002:** TLS終端とアクセス認証は、リバースプロキシ、VPN、ゼロトラストアクセス製品等の外部境界へ委譲する。
- **TP-SEC-003:** インターネットへ直接公開する場合は、外部境界によるアクセス保護を必須とし、READMEまたは運用文書で警告する。
- **TP-SEC-004:** 状態変更リクエストは同一オリジンからの操作であることを検証する。具体的なCSRF対策方式は詳細設計で決定する。

### RSS取得

- **TP-SEC-005:** 購読URLは公開されたHTTPまたはHTTPS URLだけを許可する。
- **TP-SEC-006:** DNS解決結果がloopback、private、link-local、予約済みアドレス、クラウドメタデータサービス等を指す場合は取得を拒否する。
- **TP-SEC-007:** HTTPリダイレクトごとに移動先を再検証し、検証を迂回した内部ネットワークアクセスを防ぐ。
- **TP-SEC-008:** 応答サイズ、接続時間、読み取り時間、リダイレクト回数、同時取得数へ上限を設ける。
- **TP-SEC-009:** RSS由来の題名、購読元、要約は信頼せず、HTML出力時にエスケープする。
- **TP-SEC-010:** 要約を検索対象として保存する場合は、危険なHTMLを除去してプレーンテキスト化する。対応要件: `PR-SRCH-003`
- **TP-SEC-011:** 元記事本文や画像はサーバーから取得・保存しない。対応要件: `PR-CARD-003`, `PR-SRCH-005`

## 7. UI実装方針

- **TP-UI-001:** 主要画面はサーバーサイドテンプレートで生成し、カード操作や生成状態の更新にHTMXを使用する。
- **TP-UI-002:** 元記事を開いたタブからSpinelへ戻った際の状態更新など、ブラウザ機能が必要な箇所だけ素のJavaScriptを使用する。対応要件: `PR-CARD-006`, `PR-CARD-007`
- **TP-UI-003:** CSSカスタムプロパティで色、余白、タイポグラフィ等を管理し、ライト／ダーク設定へ対応する。対応要件: `PR-UI-001`, `PR-UI-003`
- **TP-UI-004:** モバイル幅を基準に設計し、折りたたみ端末とデスクトップへ段階的に拡張する。対応要件: `PR-CTX-003`, `PR-UI-004`
- **TP-UI-005:** JavaScriptが必要な操作でも、ボタンの意味、フォーカス、キーボード操作を損なわない。対応要件: `PR-UI-005`
- **TP-UI-006:** `prefers-reduced-motion` を尊重し、重要操作をアニメーションだけで表現しない。対応要件: `PR-UI-006`

## 8. 運用

- **TP-OPS-001:** 開発環境と本番環境の双方でDockerによる実行を基本とする。
- **TP-OPS-002:** 本番はVPSまたはEC2等での常時稼働を想定する。
- **TP-OPS-003:** アプリケーションの生存確認に使えるヘルスチェック手段を提供する。具体的なURLと応答形式は詳細設計で決定する。
- **TP-OPS-004:** フィード取得失敗、生成失敗、保持期限処理の結果を、機密情報を含めずログへ記録する。
- **TP-OPS-005:** SQLiteの安全な手動バックアップと復元手順を運用文書へ記載する。
- **TP-OPS-006:** v1では自動バックアップ機能を実装しない。
- **TP-OPS-007:** Dockerホストのローカル時刻へ依存せず、日界判定に `Asia/Tokyo` を明示的に使用する。対応要件: `PR-DECK-002`, `PR-DECK-003`

Dockerイメージ、Composeファイル、環境変数、ログ形式、ヘルスチェックURL、バックアップコマンドの具体形は詳細設計で決定する。

## 9. 品質保証

### 自動テスト

- **TP-QA-001:** 選抜、日界、候補期間、期限切れ、保持期間などのドメインロジックを単体テストする。
- **TP-QA-002:** SQLite、HTTP、フィード取得、生成の冪等性、検索上限、購読解除を統合テストする。
- **TP-QA-003:** 主要なカード操作を、スマートフォン幅および折りたたみ端末相当幅のブラウザE2Eテストで検証する。
- **TP-QA-004:** SSRF防止、リダイレクト再検証、HTML無害化、応答上限をセキュリティテストで検証する。
- **TP-QA-005:** 時刻をテストから制御できる構造とし、午前5時境界、数日不在、日界をまたぐ未完了デッキを実時間待ちなしで検証する。

### CI

- **TP-QA-006:** GitHub Actionsでlint、型チェック、単体・統合テスト、主要E2Eテストを実行する。
- **TP-QA-007:** Alembicマイグレーションが空のDBへ適用できることをCIで検証する。
- **TP-QA-008:** WCAG 2.2 AAの完全準拠や自動監査はv1の必須条件にしないが、プロダクト要件の基本的なアクセシビリティを手動および主要E2Eで確認する。対応要件: `PR-UI-005`, `PR-UI-006`, `PR-UI-007`

具体的なlint、型チェック、E2Eライブラリとバージョンは詳細設計で決定する。

## 10. 詳細設計へ先送りする事項

次の事項はv1の実装前に詳細設計で決定する。本書だけから推測して固定しない。

- パッケージとディレクトリ構成
- 内部API、URL、HTTPメソッド、HTMLフラグメント構成
- テーブル、列、インデックス、列挙値
- 記事の重複判定とURL正規化の具体的アルゴリズム
- スケジューラ、RSSパーサー、HTTPクライアント、テンプレートエンジン
- 取得のタイムアウト、再試行、並行数、応答サイズ上限
- CSRF対策と秘密情報管理の具体方式
- ログ形式、ヘルスチェック形式、環境変数
- CSSの命名規則とデザイントークンの具体値

これらの詳細設計は、対応する `PR-*` 要件と本書の `TP-*` 方針に反してはならない。

## 11. v1の技術的な対象外

- 複数ユーザー向けの認証・認可・データ分離
- 複数ワーカー、水平スケール、分散ジョブ
- 外部DBを必須とする運用
- アプリ内TLS終端
- プライベートネットワーク上のフィード取得
- 元記事本文や画像の保存
- 自動バックアップ
- 公開JSON APIの提供
- テレメトリー、利用分析、外部通知
